# خطة تقسيم وتحسين أداء مشروع almajd-school

## الخلاصة التنفيذية

المشروع يعمل حالياً داخل ملف واحد `index.html` حجمه تقريباً **1.6 ميجابايت و15,735 سطراً**، ويحتوي على نحو **32 كتلة JavaScript و30 كتلة CSS**. هذا هو أكبر سبب لصعوبة الصيانة وبطء التحميل وإعادة الرسم.

أفضل مسار ليس إعادة كتابة الموقع بالكامل مرة واحدة، بل **تقسيم تدريجي بدون تغيير السلوك**:

1. تثبيت السلوك الحالي باختبارات بسيطة.
2. فصل CSS وJavaScript إلى ملفات مستقلة.
3. إنشاء طبقة بيانات واحدة للسحابة.
4. تقسيم كل ميزة إلى وحدة مستقلة.
5. تحميل الشاشات الثقيلة عند الحاجة فقط.
6. تحسين القراءة والكتابة والرسم في الواجهة.

أوصي باستخدام **Vanilla JavaScript Modules + Vite** في المرحلة الأولى بدلاً من إدخال React أو إطار كبير؛ لأن الموقع موجود بالفعل ويحتوي على واجهة جاهزة، وهذا يقلل مخاطر إعادة البناء ويحافظ على سرعة الهاتف.

## 2. مسؤولية كل طبقة

### `app`
تدير تشغيل التطبيق فقط: الجلسة، المستخدم الحالي، التبويب النشط، والصلاحيات. لا تحتوي على كود رسم الجداول أو طلبات السحابة.

### `api`
هي المكان الوحيد الذي يتعامل مع السحابة. يجب ألا تستدعي الواجهة `fetch` أو `MajdLocalDataAPI` مباشرة.

مثال:

```js
// src/api/teachers.api.js
export async function createTeacher(input) {
  return cloudClient.upsert('teachers', input.id, input);
}

export async function updateTeacher(id, patch) {
  return cloudClient.upsert('teachers', id, patch, { merge: true });
}
```

### `features`
كل ميزة تحتوي على العرض والمنطق الخاص بها. مثلاً إضافة وتعديل المعلمين تكون داخل `features/teachers`، وليس موزعة بين HTML وأماكن متعددة في الملف.

### `components`
العناصر المتكررة مثل النافذة المنبثقة، رسالة النجاح، التحميل، الجدول، والقائمة الجانبية.

## 3. ترتيب التنفيذ الآمن

### المرحلة الأولى: تثبيت الوضع الحالي

- إنشاء نسخة Git مستقلة قبل التقسيم.
- التأكد من عمل تسجيل الدخول، إضافة المعلم، تعديل المعلم، المصاريف، التقارير، والرصد.
- إضافة فحص JavaScript تلقائي في كل Commit.
- تسجيل الأخطاء المهمة في Console بشكل واضح.

### المرحلة الثانية: فصل الملفات بدون تغيير السلوك

ننقل المحتوى كما هو تقريباً:

- كل CSS إلى `src/styles` وملفات ميزات منفصلة.
- كل كتلة JavaScript إلى ملف حسب وظيفتها.
- إبقاء نفس أسماء الدوال مؤقتاً لتجنب كسر HTML الحالي.
- تشغيل الموقع عبر Vite.

هذه المرحلة يجب ألا تغيّر شكل الموقع أو طريقة استخدامه.

### المرحلة الثالثة: توحيد طبقة السحابة

إنشاء `cloudClient` يحوي:

- `list(collection, filters)`
- `get(collection, id)`
- `upsert(collection, id, data)`
- `remove(collection, id)`
- معالجة انتهاء الجلسة.
- رسالة خطأ موحدة.
- منع إرسال الطلبات بدون جلسة صالحة.

بعدها تُزال الاستدعاءات المباشرة المتفرقة من الملفات.

### المرحلة الرابعة: تقسيم الواجهة إلى ميزات

نبدأ بالميزات الأقل خطورة:

1. المعلمون داخل لوحة الإدارة.
2. الطلاب.
3. الملاحظات.
4. المصاريف.
5. التقارير.
6. الرصد اليومي والوافدين؛ لأنها الأكثر تعقيداً.

### المرحلة الخامسة: التحميل عند الطلب

لا يتم تجهيز كل الشاشات الثقيلة عند تسجيل الدخول. يتم تحميل بيانات الميزة عند فتحها لأول مرة:

- جدول المعلمين عند فتح لوحة الإدارة.
- تقارير المصاريف عند فتح المصاريف.
- التقرير الشهري عند فتح التقارير.
- بيانات الأوائل عند فتح تبويب الأوائل.

هذا يقلل وقت الدخول واستهلاك الذاكرة.

## 4. تحسينات الأداء الأكثر تأثيراً

### أ. تقليل حجم البداية

حالياً يتم تحميل كل CSS وJavaScript مع الصفحة. الهدف:

- `index.html` أقل من 100 كيلوبايت.
- تحميل كل ميزة في Chunk مستقل.
- ضغط الملفات أثناء Build باستخدام Vite.
- تحميل Chart.js وSheetJS عند الحاجة فقط، لأنهما من أكبر المكتبات.

### ب. تقليل إعادة الرسم

بدلاً من إعادة رسم كل الجداول بعد كل تعديل:

- حدّث الصف المتأثر فقط.
- استخدم `DocumentFragment` عند بناء الجداول.
- لا تستدعِ `renderDailyTable` و`renderMonthlyReport` و`renderManagerView` كلها بعد كل عملية صغيرة.
- استخدم `requestAnimationFrame` لتجميع تحديثات الواجهة.

### ج. تحسين البيانات

- لا تحمل كل سجلات السنوات عند بداية الموقع.
- استخدم pagination للتقارير الكبيرة.
- اطلب الفترة الزمنية المطلوبة فقط.
- خزّن النتائج المؤقتة بـ cache لمدة قصيرة.
- استخدم `updatedAt` لمعرفة ما يحتاج إلى تحديث.

### د. منع الطلبات المكررة

- تعطيل زر الحفظ أثناء الطلب.
- منع الضغط المزدوج.
- استخدام debounce للبحث والمرشحات.
- إلغاء الطلب السابق إذا بدأ المستخدم بحثاً جديداً.

## 5. أهم تعديل أمني يجب عمله أثناء التقسيم

حالياً جدول المعلمين يعرض كلمة المرور داخل الواجهة. هذا يجب تغييره فوراً:

- لا تُخزّن كلمات المرور كنص واضح.
- لا تُرسل كلمة المرور ضمن قائمة المعلمين.
- لا تعرضها في الجدول.
- اجعل تغيير كلمة المرور عبر Edge Function مصادق عليه.
- استخدم Hash لكلمات المرور في الخادم.
- اجعل `teachers` قابلة للقراءة والتعديل فقط لحساب admin.

التقسيم فرصة مناسبة لإصلاح هذا بدون خلطه مع كود الواجهة.

## 6. شكل تدفق إضافة المعلم بعد التقسيم

```text
نموذج إضافة المعلم
        ↓
validation.js
        ↓
teachers.service.js
        ↓
teachers.api.js
        ↓
cloudClient.upsert('teachers')
        ↓
نجاح مؤكد من السحابة
        ↓
تحديث Store محلي
        ↓
تحديث صف المعلم فقط
        ↓
رسالة نجاح
```

في حالة الفشل:

```text
فشل السحابة
   ↓
لا نغير القائمة المحلية
   ↓
نظهر سبب الفشل
   ↓
نترك النموذج كما هو لإعادة المحاولة
```

## 7. ما يجب عدم فعله

- عدم تحويل المشروع كله إلى React دفعة واحدة.
- عدم وضع كل الكود في ملف JavaScript واحد جديد.
- عدم تكرار كود طلبات السحابة داخل كل ميزة.
- عدم تحميل كل بيانات التقارير مع تسجيل الدخول.
- عدم تحديث كل الجداول بعد تعديل صف واحد.
- عدم حفظ كلمات المرور أو عرضها كنص واضح.
- عدم حذف `index.html` القديم قبل التأكد من تطابق النسخة الجديدة.

---

## 8. معايير نجاح التقسيم

يعتبر التقسيم ناجحاً إذا تحققت هذه النتائج:

- فتح الصفحة الأساسية أسرع بوضوح على الهاتف.
- تسجيل الدخول لا ينتظر تحميل كل التقارير.
- إضافة وتعديل المعلم يصلان للسحابة ويظهران بعد إعادة الدخول.
- كل ميزة يمكن تعديلها بدون لمس بقية الميزات.
- لا توجد دوال عامة كثيرة بأسماء متضاربة.
- الأخطاء تظهر للمستخدم برسالة مفهومة.
- لا تُعرض كلمات المرور في الواجهة.
- يمكن اختبار كل خدمة منفردة.

## القرار المقترح

نبدأ أولاً بتقسيم **لوحة الإدارة والمعلمين** لأنها مطلوبة حالياً ولها حدود واضحة، ثم نطبق نفس النمط على الطلاب والمصاريف والتقارير. بعد نجاح أول مرحلتين ننقل الرصد اليومي والوافدين، لأنهما يحتويان على أكبر قدر من المنطق والاعتماديات.

هذا المسار يعطي تحسيناً تدريجياً في الأداء مع أقل احتمال لتعطيل الموقع أو فقدان البيانات.
